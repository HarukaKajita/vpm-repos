## 何を書く場所か

**エージェント（Claude Code / Codex など）が Unity エディタを外から操作して開発するときに、
実際に踏んで確かめた落とし穴と、その回避手順**を溜める。

書いてよいもの:

- 実機で再現・検証した挙動（何を試して何が起きたかを含める）
- 公式ドキュメントの記述と実際の挙動が食い違った点
- エージェント特有の制約（メインスレッドが止まると何もできない、呼び出しが再送される、など）
- 却下した案と、その理由

書かないもの:

- 検証していない推測。「たぶんこうだろう」は 1 行も混ぜない
- 商品固有の設計判断（各リポジトリの `docs/` に書く）
- 価格・未発売製品名・出品戦略（この資料群は**公開リポジトリにも配る**ため）

## なぜテンプレートが正本なのか

| 候補 | 判断 |
|---|---|
| **テンプレートリポジトリ（採用）** | 開発の標準（第 1 層）を既に所有し、sha256 による drift 検出と鮮度台帳を備えた配布機構がある。配布されたコピーが各リポジトリに在るので、**そのリポジトリだけを開いたセッションでも読める** |
| MySite | パイプラインの運用の正本（どのリポジトリが存在するか・商品情報）であって、開発の知見の置き場ではない。MySite を開いていないセッションからは読めない |

**ゴールド標準とは別のコンポーネントとして配る。** ゴールド標準には価格方針・未発売製品名・出品戦略が
含まれるため公開リポジトリへ配れないが、この資料群は純粋に技術的なので**公開リポジトリにも配れる**。
分けておかないと、公開リポジトリのエージェントがこの知見を永久に読めない。

## 書き足すときの作法

1. **どのリポジトリでの出来事か、いつ確かめたかを書く。** 後から「まだそうなのか」を確かめられるようにする。
2. **再現手順と観測値を書く。** 「うまくいかない」ではなく「A を渡すと B という例外になり、C を渡すと通る」。
3. **Unity のバージョンを書く。** 挙動はバージョンで変わる。
4. 既存の文書に入る内容なら新しいファイルを作らず追記する。索引が長くなるほど読まれなくなる。
